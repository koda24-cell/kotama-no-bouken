- 担当：Claude
- 親仕様：`MASTER_SPEC.md`
- 優先順位：ゲーム体験を成立させるロジックを担当。画面レイアウト・CSSの大規模変更はGPTへ任せる。
- 対象：マップ構造・通行／発見ロジック、FOE AI、宝箱・採集・探索記録、敵・ボス・状態異常・戦闘バランス、必要なセーブ処理。

## 1. 最上位指示

**『世界樹の迷宮』の迷宮探索と戦闘ルールを、実際のゲームプレイとして再現すること。**

見た目だけを似せる作業ではない。プレイヤーが地図を読み、通路・扉・隠し通路を探し、FOEの巡回を観察して回避し、採集と宝箱で装備を整え、弱点・状態異常・敵の行動パターンを利用して階層ボスを攻略する流れを成立させる。

## 2. 実装対象（3項目ずつ進める）

### A. 迷宮構造・扉・隠し通路
- 現行の `data/field-maps.js` 等のマップ定義と `field.js` の移動・発見処理を調査する。
- 床・壁・通路・扉・階段・隠し通路を、見た目だけでなくゲームルールとして定義する。
- 扉は開閉状態・通行可否・必要条件を一貫して管理する。閉扉を通り抜けたり、壁越しに移動したりできないこと。
- 隠し通路は通常時に未発見とし、適切な位置・条件・操作で発見できるようにする。発見後は通行可能となり、地図記録へ反映する。
- 隠し通路の存在を未発見状態でHUD・マップ・ログから漏らさない。
- マップ生成・配置を変更する場合、階段・ボス門・セーブ地点・イベントへの到達可能性を保つ。
- 迷路構造は単調な一本道にせず、分岐・袋小路・回り道・ショートカット・危険地帯を組み合わせる。ただし理不尽な詰みを作らない。

### B. FOEの巡回・追跡・回避
- FOEごとに巡回ルートまたは移動パターンを定義し、プレイヤーが観察・学習できるようにする。
- FOEは通常敵より明確に強くする。パーティを壊滅させる強さを許容するが、強さと回避可能性をセットで設計する。
- FOEの索敵・追跡・経路探索は壁・閉じた扉・通行不可タイルを考慮する。
- 追跡中はプレイヤーとの距離・経路に応じて移動し、視界を失った後の追跡継続／解除条件を明確にする。
- FOEの移動先が他の敵・壁・扉・階段・イベントオブジェクトと衝突しないようにする。
- FOEが細い通路や出口を塞いで進行不能にしない。配置・経路・移動周期を設計し、すり抜け不能の場所でプレイヤーを挟み撃ちにしない。
- FOEの位置・行動が予測不能なランダム移動だけにならない。プレイヤーが観察して回避計画を立てられる規則性を持たせる。
- 接触時はFOE専用戦闘として開始し、通常エンカウントと報酬・戦闘演出・記録を区別する。
- FOEを倒した場合は再出現条件・素材・図鑑記録を一貫して管理する。

### C. 宝箱・採集・探索記録・セーブ
- 宝箱は発見・未開封・開封済みを区別し、同じ宝箱から報酬を重複取得できないようにする。
- 採集点は採集種別（採取／伐採／採掘など）を区別し、採集可能・採集済み・再出現状態を管理する。
- 採集点の再出現条件は、階層・フロア移動、一定歩数、休息など、既存の進行に合う一貫した方式を選ぶ。条件を決める前に現行仕様を調査し、報告する。
- 採集結果は階層・フロア・採集種別と素材テーブルを対応させる。
- 発見済み・取得済みの情報は地図・図鑑・素材・ショップに反映する。
- 発見前の宝箱・採集点・イベント位置や総数を表示しない。
- セーブデータに記録する場合は既存形式を確認し、`saveVersion` とマイグレーションを用意する。旧セーブで未定義値があっても正常に読み込めること。
- 既存の素材売却・装備製作・ショップ解放と接続する。

## 3. 戦闘バランス・状態異常・ボス

### 3-1. 敵の役割と難易度曲線
- 敵を「通常敵」「階層終盤の強敵」「FOE」「階層ボス」に分類し、役割を混同しない。
- ユーザー指摘の「階層ボスより階層終盤の敵が強い」問題を必ず検証する。
- 階層終盤の通常敵は、数値だけでボスを上回らない。危険な複数体構成・連携・状態異常・属性攻撃で強さを表現する。
- 階層ボスはHPだけ高い敵ではなく、専用の行動パターン、予兆、フェーズ、弱点を突く機会、対策の必要性を持つ。
- FOEはボスと同等またはそれ以上に危険でもよいが、遭遇回避可能なフィールド強敵として役割を分ける。
- 敵の攻撃力・耐久力・速度・耐性を階層進行に合わせて調整し、パーティのレベル・装備更新・人数を基準にする。

### 3-2. 状態異常・封じ
- 現状の状態異常が緩いという指摘を前提に、付与率・持続・効果・敵耐性を総合的に見直す。
- 状態異常は戦闘の判断を変える強さを持たせる。毒・麻痺・睡眠・混乱・封じ・能力低下など、実装済みIDと効果を先に棚卸しする。
- すべての敵に同じ耐性を設定しない。種族・階層・ボスごとに弱点と耐性を設ける。
- 状態異常の付与率を上げる場合、重ね掛け・連続行動不能・回復不能のループを防ぐ。
- 回復・解除手段、耐性装備、スキル、行動選択で対抗できるようにする。
- 治癒士のリフレッシュ等、既存解除スキルの価値・SPコスト・解除範囲を状態異常の強さに合わせて調整する。
- 付与率は命中・LUC・敵耐性など既存ステータス計算との整合性を確認し、個別スキルだけに固定値を足す場当たり調整を避ける。

### 3-3. ボス行動
- 各階層ボスに個別の行動傾向と攻略要素を持たせる。
- 危険行動は予兆を出し、プレイヤーが防御・回復・封じ・弱点攻撃などを選べる余地を作る。
- フェーズ変化・HP閾値・部位／状態変化を使う場合、既存の変身・勝敗判定・報酬処理と衝突しないようにする。
- 15ターン強制敗北など既存の特殊ルールは、最終ターンで撃破した場合に勝利判定が優先される等、勝敗処理の優先順位を保つ。
- ボス専用素材・装備解放・図鑑記録を接続する。

## 4. GPTとの担当境界
- GPTは画面レイアウト・地図の描画・凡例・HUD・見た目の情報設計を担当する。
- Claudeはゲーム状態・判定・敵AI・データ・戦闘数値・セーブを担当する。
- GPT側に表示用データが必要な場合、データ名・型・更新タイミング・未発見時の扱いを明記して依頼する。
- Claude側で画面表示のためにHTML/CSSを変更する必要がある場合、最小限にとどめ、GPTと作業範囲を共有する。
- 同じファイルを同時編集しない。関連PR・作業ブランチを確認する。

## 5. 実装前の必須調査
1. `development` の最新コードと関連データを確認する。
2. 既存PR #49〜#56（戦闘数値・FOE素材等）および #66〜#91（探索・FOE・UI）の内容と未統合差分を確認する。
3. 現行のマップ、FOE、敵定義、状態異常、ボスAI、素材・宝箱・採集、セーブ構造を棚卸しする。
4. 既存実装・未実装・不具合・推測を一覧化する。
5. 3項目程度の実装単位と変更予定ファイルを提示してから着手する。

## 6. 変更禁止・注意事項
- `main` へのマージは禁止。ユーザーの明示承認が必要。
- 既存の固定ID・報酬・ストーリーイベント・素材を無断削除しない。
- セーブ形式を変更する場合はマイグレーションを用意し、旧セーブを保持する。
- マップ視界半径約4マスを無断で変更しない。
- FOEを強くするだけで回避ルートを保証しない実装は禁止。
- 既存のドラゴン／魔王変身、撃破、報酬、BGM、15ターン判定など特殊処理を壊さない。
- 他AIの未統合PRを無視して同じ箇所を再実装しない。
- 既存コードの現物を確認せず、存在しない関数・データ構造を前提に実装しない。

## 7. 完了条件
- FOEが規則的に巡回し、発見・追跡・追跡解除が成立する。
- プレイヤーが地形と巡回パターンを利用してFOEを回避できる。
- FOEが通路・階段・出口を不当に封鎖しない。
- 扉・隠し通路が実際に通行・発見ルールとして動作する。
- 宝箱・採集点が発見・取得・再出現・記録を持つ。
- 敵の難易度曲線で階層ボスの格が保たれる。
- 状態異常が戦術的に有効で、対策も成立する。
- 旧セーブ互換性を維持する。
- 各機能が報酬・図鑑・装備製作・階層進行へ接続される。
- 未確認事項を明示し、ブラウザ・実機テストを実施したと偽らない。
