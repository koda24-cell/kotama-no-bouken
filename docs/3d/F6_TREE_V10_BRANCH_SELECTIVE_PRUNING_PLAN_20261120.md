## V10で修正すべき枝ノード削除アルゴリズム
1. **最初にGLBを構造検査**。各scene nodeについて名前、mesh名、親子関係、world transform、world AABB、中心、頂点数、表面積をJSONへ出力。葉カード、幹、主枝を保護セットに入れる。名称だけで削除判定しない。
2. **枝の骨格を取得**。可能なら生成元の枝始点・終点・半径をメタデータから読む。なければ細長い枝メッシュの主軸をPCAで推定するが、曲がった枝には誤差が出るので候補リストのみ生成し自動削除しない。
3. **分岐集中を定量化**。各枝の根元から幹方向へ距離を測り、根元の高さ・方位・分岐角が近い枝をグループ化する。仮の閾値は高さ差が樹高の0.04以下、方位差15°以下、軸方向差20°以下（実画像とモデル寸法で再調整）。
4. **削除より先に優先順位を付ける**。葉塊まで連続した枝・外周樹冠を支える枝・7本の主枝を残す。短い重複細枝、葉に届かない孤立枝、同一方向に重なった枝先を優先して候補化する。
5. **枝の取り方は段階的に**。1候補群あたり最初は最大1ノード、全枝数の最大10%までを一次変更上限とし、枝の保護セットとその子孫が削除対象にないことをassertする。樹冠の中央だけが空かないよう左右・奥行きの分布も比較する。
6. **枝先を葉束へつなぐ**。残った枝の先端と最寄り葉塊の距離を測り、樹高比で距離が大きい枝は長さ/方向修正候補にする。葉カードの全体密度を再び均一化する処理は行わない。
7. **比較出力**。V08 / V09 / V10 の正面・側面・斜め、さらに分岐接写を**実GLB**から同一カメラと照明でレンダリング。透明葉、枝突き抜け、穴の増大をチェック。可能ならBlender 5.3およびThree.js双方で確認。
8. **安全性**。原本のSHA256を検証し、別名V10へ出力、差分ノード一覧/残存主枝数/葉メッシュ数/樹冠AABB/GLB SHA256をmanifestに保存。候補は未承認で正式フォルダへ昇格しない。

## 受け入れ基準（画像目視が必須）
- 7主枝・幹とV08の葉群6メッシュを保持
- 幹中央の「枝の束」状の交差が減る
- 中央に大きな穴を再発させない
- 枝先が葉塊へ自然につながり、先端だけ露出しない
- 正面・側面・斜め・接写の実レンダリングが確認可能
