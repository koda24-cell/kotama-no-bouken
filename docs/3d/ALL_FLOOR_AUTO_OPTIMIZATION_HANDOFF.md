# 全階層3Dモデルの自動軽量化：運用・安全境界（2026-11-17）

対象: 第1〜第6層および共有3Dモデル。**3Dが未統合の階層は、モデルがGitへ入った段階から処理対象にする**。最新の開発統合先は `development`、ゲームの正式素材昇格には別途ユーザー承認が必要。

## 制作時の指示方法

ユーザーは従来どおり「木を作る」「岩壁をリアルに」「レンダリングして修正を繰り返す」と指示すればよい。制作担当は以下をデフォルト工程として行う。

1. 原本のBlender/GLBを品質最優先で造形。材料・材質・枝/葉/形状を、後で安全にまとめられるよう分類する。特に繰返しパーツは同じ材質を再利用する。
2. 正面・側面・斜め、必要なら上面を実レンダリング。ユーザーが外見を承認するまで形状・質感を勝手に削らない。
3. GLB生成後に共通構造監査を実行し、mesh nodes、三角形、primitive instances、透過材質、容量を記録。**GLB内部の描画単位と実機のdraw calls/FPSは異なる。**
4. **静的・不透明・リグなしの岩/建造物**は非破壊LOD0/1/2候補を作る。**樹木・草など**は葉を材質別にまとめ、葉束/8方向Impostorを検討。**水、溶岩、霧、魔法VFX、ガラス、キャラ**は専用の処理で個別検証。
5. 同一カメラ・照明で原本と軽量版のPNGを比較し、FPS/draw calls/描画のちらつきをThree.jsで計測。画質劣化、タイルの継ぎ目、ゲーム機能への副作用があれば採用しない。
6. 原本と軽量候補の保存先を分け、manifestに品質・検証・承認状態とハッシュを記録。**技術QAが通っても未承認のモデルを正式素材フォルダ/ゲームに組み込まない**。

## GitHub Actionsで現在自動化した範囲

- `.github/workflows/shared-3d-performance-audit.yml`: 全階層の既存GLBを構造監査、素材分類と階層別レポートを保存する（第6層など、まだファイルがない階層は空欄）。
- `.github/workflows/auto-review-new-3d-assets.yml`: `development`へのpushまたはPRでGLBが追加・変更された場合、全階層を監査して変更された静的・不透明な適格ファイルだけを抽出。`shared-rigid-lod-review.yml`で**未承認のLOD0/1/2比較用アセット**を生成。1回のPRで複数ファイルの場合は同時2ジョブまで。スキニング、透過、VFX等は意図的に自動Decimateしない。
- 植生の材質別葉統合と8方向ImpostorはGitHub Actionsで実レンダリングまで検証された専用フロー。枝の修正・承認前アセットはゲームに組み込まない。
- `tools/3d-performance/lod_policy.mjs`はヒステリシス付きLOD判定と2Dセル先読みのテスト実装だが、**全階層のゲーム実描画とはまだ接続していない**。
- 新規モデルの**生成結果がActions Artifactsの中にしか存在しない**ときは、GitHubへのコミット監視では捕捉されない。生成側のワークフロー内で共通監査を呼ぶか、別途Artifacsのレビューを実行すること。これはユーザーへの依頼ではなく制作担当の義務。
- `main`への自動マージはしない。既存機能、セーブ、マップ、キャラクター、衝突、VFX時系列処理を変えない。

## 全階層3D表示の現状と限界

- 現状 `field/field-3d-view.js` は通常の第1〜第5層の3D表示を制御している（第6層の実行時接続は別途確認）。第3層は既存の一部LOD・InstancedMeshを使用し、第4・第5層の静的部品もInstancedMeshを使用。全階層共通の距離LODストリーミングマネージャーは未導入。
- カメラから遠いからという理由で壁や階段、イベント用の当たり判定を消す処理は危険。まず静的な描画だけの切替から実機検証を行う。
- 最適化アセットを自動生成することと、ゲーム内でそのアセットを自動表示切替することは異なる。実ゲームでのLOD切替は正しいファイル配置と性能・視覚レビュー、ユーザーの正式承認を経て導入する。
