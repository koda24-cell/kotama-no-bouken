# Claude作業仕様書：既存データ・資料の棚卸しと構造整理

- 対象プロジェクト：`kotama-no-bouken`
- 担当：Claude
- 基準ブランチ：`development`
- 作業ブランチ：`feature/ai-claude-data-reorganization-spec`
- 作業開始基準コミット：`1dd7ade34f0a95ef7c355512c6eaf09cb8d552ee`
- 目的：古い資料・重複データを整理し、長大な資料・データ・コードを今後修正しやすい単位に分割する
- 重要度：高
- 作業方式：段階的な調査・整理。大規模変更を一度に行わない

---

## 1. 作業目的

現在のリポジトリには、過去の仕様書・作業メモ・引き継ぎ資料・実装メモが複数存在する。また、一部のJavaScriptや固定データは長大で、目的の記述を探しにくく、複数AIの同時作業で競合しやすい。

今回の作業では、次の状態を目指す。

1. 現在の `development` と一致しない古い説明・重複資料を特定する。
2. 同じ内容を複数箇所に持つ資料は、正本を決めて参照方式に整理する。
3. 役目を終えた資料は、必要な履歴を残したうえでアーカイブする。
4. 文字数・行数が多く、修正箇所を探しにくいデータやコードを、機能・階層・用途単位に分割する。
5. 分割後も既存ゲームの挙動、画面、セーブデータ、ID、素材参照を変えない。
6. AIが次回以降の作業で迷わないよう、リポジトリ案内資料を現状に合わせて更新する。

これは整理・保守性向上の作業であり、新機能の追加やゲームバランス変更は目的ではない。

## 2. 最優先ルール

### 2-1. 最新developmentを基準にする

作業開始時に、GitHub上の最新 `development` を再確認する。仕様書作成時点の基準コミットは上記のとおりだが、Claudeが作業を開始する時点で新しいコミットが存在する場合は、その最新状態を基準に作業ブランチを更新する。

- `main` は変更しない。
- `development` へ直接コミットしない。
- 作業ブランチで作業し、完了後は `development` 宛てPRを作成する。
- PRのマージはユーザーが行う。Claudeはマージしない。
- 他AIの作業ブランチを変更しない。
- force push、履歴書き換えを行わない。

### 2-2. 既存仕様・セーブデータの保護

以下はユーザー承認なしに変更・削除しない。

- キャラクター、職業、敵、アイテム、スキル、イベント、実績、素材等の固定ID
- セーブデータの構造、保存キー、saveVersion、移行処理
- ゲーム内数値、確率、報酬、敵行動、戦闘順、状態異常の仕様
- 既存の画像・音声・その他アセットとそのファイル名
- 外部ライブラリ、外部サービス、認証・公開設定

データをファイル間で移動する場合も、値・キー・配列順・参照先を変えない。セーブデータの移行処理が必要になる変更は今回の範囲外とし、理由と案を報告して承認を待つ。

## 3. 最初に行う現状調査（実装前必須）

まず最新 `development` を読み、以下を調査する。

### 3-1. 資料・ドキュメント

対象例：

- `AI_DEVELOPMENT_RULES.md`
- `AI_HANDOFF.md`
- `CHATGPT_PROJECT_PROMPT.md`
- `ASSETS_CREDITS.md`
- `docs/PROJECT_CURRENT_STATE.md`
- `docs/` 以下の仕様書、タスク指示書、レビュー記録、実装メモ
- `data/README.md`
- `css/README.md`
- `field/README.md`
- `references/` 以下の案内資料

各ファイルを次の区分に分類し、一覧表にする。

| 区分 | 意味 | 基本対応 |
|---|---|---|
| 現行正本 | 現在の仕様・ルールとして参照すべき資料 | 維持・更新 |
| 現行補助資料 | 正本を補足する資料 | 維持・リンク整理 |
| 重複 | 他資料と内容が重なっている | 正本へ集約し、重複側は短い案内へ |
| 旧版・失効 | 現行仕様と異なる、または役目を終えた資料 | 履歴価値を確認してアーカイブ |
| 作業記録 | 過去のPR・レビュー・検証の記録 | 原則保存。必要ならアーカイブ |
| 未確定・要確認 | 内容の正誤や採用状態を判断できない | 削除せず、未確定として報告 |

ファイル名や更新日だけで古いと判断しない。現行コード・PR・仕様との照合を行う。

### 3-2. 古い情報・矛盾の確認

特に次を重点確認する。

- 既にマージ済みのPRを「未マージ」と記載していないか。
- 統合済み・中止済みの作業が「作業中」と記載されていないか。
- 古いブランチ名、古いファイル構成、古い読み込み順が残っていないか。
- 仕様書と実際の `development` の実装が異なっていないか。
- 同じ仕様が複数の資料に別々の表現で記載されていないか。
- 作業指示書が、現在のファイル構成や担当分担と矛盾していないか。

現状を確認できない記述は、推測で書き換えず「未確認」と明記する。

### 3-3. 長大ファイル・データの調査

全ファイルのサイズ・行数を一覧化し、特に次を確認する。

- `script.js`
- `battle-ext.js`
- `field.js` と `field/` 以下
- `data/field-maps.js`
- `data/story.js`
- `data/items.js`
- `data/jobs.js`
- `style.css` と `css/` 以下
- 長大なMarkdown仕様書・タスク資料

文字数だけを基準に機械的に分割しない。機能、データの責務、依存関係、更新頻度、担当AIの競合範囲を考慮する。

## 4. 整理・分割の基本方針

### 4-1. ドキュメントの正本を明確にする

原則として、次の役割を分ける。

- `AI_DEVELOPMENT_RULES.md`：全AI共通の開発・Git運用ルール
- `CHATGPT_PROJECT_PROMPT.md`：ChatGPT向けの常設引き継ぎ指示
- `AI_HANDOFF.md`：リポジトリ全体の構造、読み込み順、注意点、案内
- `docs/PROJECT_CURRENT_STATE.md`：developmentに実在する現状、未統合PR、確認状況
- `docs/` 以下：機能別の仕様書・タスク・検証記録
- 各フォルダの `README.md`：そのフォルダ内のファイル役割と編集ルール

同じ説明を複数ファイルに長文で複製しない。詳細は正本に置き、他資料から相対リンクで参照する。

ただし、AIが最初に読む必要がある重要ルールは、リンクだけにして見落とされないようにする。

### 4-2. 古い資料の扱い

- 重複内容は、正本を決めて統合する。
- 旧仕様書・旧タスク指示書は、現行資料と混同しないよう `docs/archive/` 等への移動を検討する。
- PRレビュー記録や検証履歴は、将来の判断根拠になるため、原則として削除しない。
- リンク切れが起きないよう、移動時は参照元をすべて更新する。
- 削除が必要と判断した場合は、対象・理由・代替先を一覧にし、削除前に報告する。判断に迷うものは残す。

### 4-3. 長い仕様書・Markdownの分割

分割候補は、章ごとに独立して参照・更新できる場合に限る。

推奨構成例：

```text
docs/
  feature-name/
    README.md          # 全体案内・目次・適用状態
    OVERVIEW.md        # 全体方針
    SYSTEM_SPEC.md     # システム仕様
    DATA_SPEC.md       # データ定義
    UI_SPEC.md         # UI・演出
    TEST_PLAN.md       # テスト方法
    TASKS/
      CLAUDE_TASK.md
      GPT_TASK.md
```

上記は例であり、既存資料を無理にこの形へ統一しない。分割後は必ず入口となるREADMEまたは目次を置く。

### 4-4. 長いゲームデータ・コードの分割

分割は、実際の依存関係と読み込み方法を調査してから行う。

候補例：

- `data/field-maps.js`：階層別・フロア別に分ける案
- `data/story.js`：階層別・イベント種別に分ける案
- `script.js`：画面、編成、ショップ、成長、戦闘、セーブ等の機能単位に分ける案
- `battle-ext.js`：責務が明確に独立している場合のみ機能単位に分ける案
- `style.css`：既存の読み込み順・上書き関係を保てる場合のみ分割する案

特に `script.js` はグローバル変数・関数・イベント登録・初期化順の依存があるため、一括分割しない。1機能ずつ移し、移動前後の挙動を確認する。

#### 分割時の必須条件

1. 既存のグローバル名、関数名、ID、データ値を原則維持する。
2. 現在のクラシックスクリプト方式を維持する。ES Modules化やビルド環境導入は今回行わない。
3. `index.html` の読み込み順を明示し、依存先より後に実行されることを保証する。
4. 既存の初期化処理・イベント登録が二重実行されないこと。
5. 配列の並び順、乱数の呼び出し順、オブジェクトの参照関係を不用意に変えない。
6. `?v=` キャッシュ番号を更新する場合、最新developmentの最大値を確認して一貫して更新する。
7. 分割前後で、ゲームの表示・進行・戦闘・セーブに差がないことを確認する。
8. 分割だけで解決できない設計問題は、勝手に仕様変更せず別提案にする。

## 5. 実作業の進め方

大規模な整理を一つの巨大PRにまとめない。次の段階に分ける。

### Phase 1：棚卸し・整理計画

- 最新developmentの全資料・全データファイルを調査。
- 重複、旧版、矛盾、長大ファイルを一覧化。
- 正本・参照先・アーカイブ候補を決める。
- 分割後のフォルダ構成案を提示する。
- 変更によるリスク、テスト方法、競合しそうなファイルを明記する。

この段階では、削除や大規模なコード移動を行わない。

### Phase 2：ドキュメント整理

- 現行の正本を明確にする。
- 古い進捗・PR状態・ファイル構成の説明を最新developmentに合わせる。
- 重複した説明を集約し、リンクへ置き換える。
- 必要な旧資料をアーカイブする。
- README・目次・相互リンクを更新する。

### Phase 3：固定データの分割

- `data/` の長大データを対象に、責務が明確なものから段階的に分割。
- まずは `field-maps.js`、`story.js` など、分割単位を作りやすい候補を検討する。
- データ値・ID・配列順を変えない。
- `index.html` の読み込み順を更新する。
- `data/README.md` も同時に更新する。

### Phase 4：ゲームロジックの分割

- `script.js` 等の長大なロジックを機能単位で分割。
- 1回の変更で移動する範囲を限定する。
- 既存の関数・状態・イベントの依存関係を記録する。
- `AI_HANDOFF.md` の読み込み順・ファイル案内も更新する。
- 競合が大きい場合は無理に進めず、次のPRに分ける。

### Phase 5：最終検証・報告

- 分割前後の差分を確認し、意図しない値・処理変更がないことを検証。
- 構文チェック、参照先チェック、リンク切れチェックを行う。
- 実行できる自動テストを実行する。
- ブラウザ・iPhone実機で確認していない場合は、必ず未確認と報告する。
- PRには変更内容、移動対応表、テスト結果、未確認事項、残課題を記載する。

## 6. テスト・品質基準

最低限、次を確認する。

- JavaScript：対象ファイルに `node --check` を実行。
- `index.html`：読み込み先の存在、読み込み順、重複読み込みを確認。
- データ：分割前後のキー・ID・数値・配列順・件数を比較。
- ゲーム：起動、画面遷移、編成、ショップ、戦闘、探索、セーブ/ロードの影響を確認。
- セーブ：既存セーブを壊さない。saveVersionを変更しない。
- CSS：分割前後の連結順とルールの優先関係を確認。実機表示未確認なら明記。
- Markdown：相対リンク切れ、古いブランチ名、古いPR状態の残存を確認。

「コードが構文エラーなし」だけで「動作確認済み」と扱わない。

可能な場合は、分割前後でデータのJSON化比較や固定乱数による戦闘結果比較を行う。比較ができない箇所は理由を明記する。

Phase 1の監査・計画が完了した時点で、実装に進む前に一度報告する。大きなリスクや仕様変更が必要な場合は、実装を止めてユーザーに判断を求める。

## 8. 完了報告の形式

PR本文およびClaudeの報告には、次を含める。

- 最新developmentの基準コミット
- 変更ファイル一覧
- 統合・アーカイブした資料と理由
- 分割したファイルの旧名 → 新名対応表
- データ値・固定ID・セーブ互換性に変更がないことの確認方法
- 実行したテストと結果
- ブラウザ/iPhone実機の確認有無
- 未対応・保留・ユーザー判断が必要な項目
- 次の段階で推奨する作業

**最終原則：読みやすさ・修正しやすさ・AI間の作業競合の減少を優先する。ただし、整理のためにゲームの挙動や既存データを犠牲にしない。**
