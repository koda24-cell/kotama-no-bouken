# 一人称3D迷宮 技術設計・試作仕様

- 対象：kotama-no-bouken
- 作業ブランチ：feature/gpt-first-person-3d-prototype
- 基点：development
- 担当：GPT（3D描画基盤・技術設計）
- 状態：設計確定前の試作仕様。mainへの反映は禁止。developmentへの直接統合もしない。
- 目標：B1F「はじまりの樹海」を現代JRPG級の品質で一人称3D迷宮として探索可能にする。

## 1. 基本方針

既存の迷宮ゲームロジックを作り直さず、既存のグリッドマップ・状態管理を正とする。Three.jsは表示専用の3Dビューとして追加し、ゲームルールと描画を分離する。

- マップ、座標、壁判定、扉、隠し通路、仕掛け、宝箱、採集、イベント、FOEの移動・AI、探索記録、セーブデータは既存実装を正とする。
- 3D側で独自のマップ状態や別の衝突判定を持たない。
- 既存の2D探索画面はフォールバックとして残し、3D試作が失敗しても通常プレイを壊さない。
- 最初はB1Fの限定区画だけで有効化し、他階層へ一括適用しない。
- 既存セーブ形式を変更しない。表示モード設定を保存する場合も既存セーブ互換性を壊さない方法を別途検討する。

## 2. 現行構造の確認事項

developmentブランチで確認したファイル：

- `field.js`：探索状態・共通定数等の入口
- `field/field-render.js`：現在のDOM探索画面、ミニマップ、全体マップ描画
- `field/field-movement-foe.js`：移動・FOE関連処理
- `field/field-navigation.js`：探索ナビゲーション
- `field/field-persistence.js`：探索状態の保存関連
- `field/field-interactions.js`：オブジェクト操作
- `field/field-puzzles.js`：仕掛け
- `data/field-maps.js`：階層・フロア・マップ・objects・FOEデータ

現行の探索表示はDOM/CSS方式で、ミニマップ・全体マップはCanvas 2Dで描画されている。マップデータのコメントでは1文字=1マス、32px単位と定義されている。現時点でリポジトリのルートにpackage.jsonやVite設定は確認できていない。3D導入前に最新ブランチとの差分を再確認すること。

## 3. 推奨アーキテクチャ

### 3.1 責務分離

| 層 | 責務 | 正とするデータ |
|---|---|---|
| Game Logic | 移動可否、イベント、扉、仕掛け、FOE AI、セーブ | 既存field系 |
| Grid Adapter | グリッド座標・方向・オブジェクト・FOE状態を3D座標へ変換 | 既存fieldState / FIELD_AREAS |
| Three View | 床・壁・天井・装飾・光・霧・カメラ描画 | Adapterから受け取る読み取り専用状態 |
| Input Adapter | タップ/キーボード入力を既存移動・操作関数へ橋渡し | 既存入力関数 |
| Cartography UI | ミニマップ・全体マップ | 既存Canvas描画を継続利用 |

### 3.2 追加候補ファイル

- `field/3d/field-3d-scene.js`：Renderer、Scene、Camera、ライフサイクル
- `field/3d/field-3d-grid-adapter.js`：既存マップから3D座標・セル種別を取得
- `field/3d/field-3d-world.js`：床・壁・天井・環境メッシュ生成
- `field/3d/field-3d-objects.js`：扉・宝箱・採集地点等の表示
- `field/3d/field-3d-foes.js`：既存FOE位置の表示同期
- `field/3d/field-3d-input.js`：一人称操作入力の橋渡し
- `css/09-labyrinth-3d.css`：3D画面・タッチ操作UI

これは候補構成であり、実際の追加時に既存の読込順・命名規則に合わせて調整する。

## 4. 座標変換ルール（初期案）

- 1グリッド = 4 Three.js world units。
- グリッド座標 `(tx, ty)` の中心を `x=(tx+0.5)*4`、`z=(ty+0.5)*4` とする。
- 画面上の前方（既存の `up`）はワールド座標の `-Z` 方向。
- `right` は `+X`、`down` は `+Z`、`left` は `-X`。
- 壁の高さは初期値4 world units。天井高・通路幅は素材に合わせて調整可能にする。
- 既存のピクセル座標は `FIELD_TILE` を用いてグリッド座標へ変換する。32pxをコード内に再ハードコードしない。
- 方向転換は既存のdir状態を参照し、3Dカメラのyawへ変換する。

数値は試作開始用の仮スケールであり、既存ゲームデータの値を変更するものではない。

## 5. 入力・移動

### タッチUI
- 中央：前進
- 左右：90度旋回
- 下側：後退
- 扉・宝箱・採集地点・仕掛け等が操作可能範囲にある場合は対象物操作を優先
- 連続タップによる多重移動を防止し、移動中は入力ロック
- 既存の会話・ダイアログ・マップ表示・戦闘遷移中は探索移動を受け付けない

### PC
- 既存のキーボード操作を維持する。
- マウス操作は追加候補とし、タップUIと競合しないようにする。

### ロジック接続
3D側から座標を直接書き換えない。既存の移動・操作関数を呼び出し、処理完了後のfieldStateを再描画する。関数名・引数は実装時に現行コードで再確認し、推測で呼び出さない。

## 6. マップ描画

- `FIELD_AREAS`内の現在フロアのmapを読み、通行可能セルに床、壁セルに壁を生成する。
- 壁の種類・扉・仕掛け・隠し通路などは既存の判定関数とobjectデータを参照する。
- 外周壁を含め、既存マップの衝突判定と見た目を一致させる。
- 床・壁・天井はマテリアル共有とジオメトリ結合を優先し、セルごとの大量Mesh生成を避ける。
- 最初の試作では床・壁・天井・簡易照明を完成させてから装飾を足す。

## 7. B1F「はじまりの樹海」アートディレクション

テーマ：古代遺跡に侵食された深い森。美しさと不気味さを両立する。

### マテリアル
- 石：湿った古代石、欠け・ひび・苔・水染み
- 根：太い樹木の根が石壁や天井を貫通し、自然に侵食
- 地面：土、落葉、苔、石畳の混在
- 植物：シダ、蔓、菌類、小さな発光植物
- 金属：古代遺跡の鈍い青銅・黒鉄

### 光・空気
- 基調は深い緑と青緑。完全な黒つぶれは避ける。
- 木々の隙間から差す局所的な光芒。
- 遠景に薄い霧、低い位置に控えめな靄。
- 発光植物や古代装置は青白い補助光。
- 浮遊粒子は密度を抑え、画面を濁らせない。
- 明暗差で通路の奥行きと進行方向を誘導する。

### 高品質の基準
- PBRマテリアル、法線/ラフネスマップを活用する。
- GLB/glTFを基本素材形式とする。
- 近景は高密度、遠景はLODや簡略モデルを利用する。
- 重要なランドマークはシルエットだけでも識別できること。
- テクスチャはアトラス化・圧縮を検討し、同一素材を共有する。

## 8. B1F試作区画

小規模な検証用区画に次の要素を含める。

1. 一本道：一人称視点の奥行き、床・壁・天井の品質確認
2. 左右分岐：旋回・方向認識・ミニマップ同期確認
3. 古代遺跡の扉：閉/開状態と既存イベント処理の同期
4. 採集地点：対象物の視認性と操作優先順位
5. 宝箱：開封状態の反映
6. FOE出現場所：既存AI位置と3D表示の同期
7. 地下階段：フロア遷移の既存処理との接続

最初は既存マップ内にある実データの区画を選ぶ。試作専用に既存の本番マップを改変しない。必要なら別の試作データを用意する。

## 9. Three.js導入方式の判断

現行リポジトリは静的HTML/JS構成で、ルートにpackage.json/Vite設定が見当たらないため、導入方式は試作前に小さく検証する。

- CDN + ES Modules：初期変更が少ない。GitHub Pagesで利用可能。ただし外部CDNへの依存、オフライン動作、バージョン固定、アドオンの同一配信元管理が必要。
- npm + Vite：依存管理・ビルド・アセット処理に強く、3D機能拡張やテストに向く。一方、既存の静的スクリプト構成へビルド工程を追加する影響がある。

推奨：最終的に3D素材・アドオンが増える本格運用ではnpm + Viteが有力。ただし既存プロジェクト全体を一度に移行せず、試作ブランチで最小構成を検証し、GitHub Pagesへの出力・既存スクリプトとの共存・iPhone実機動作を確認してから決める。CDNを採用する場合もThree.js本体とaddonsを同じバージョン・同一CDNに固定する。

## 10. iPhoneを含む性能要件

高品質を目標にするが、操作不能になる負荷は許容しない。

- WebGL2非対応・初期化失敗時は既存2D探索へ戻す。
- devicePixelRatioを無制限に使わず、描画解像度に上限を設ける。
- 高品質/標準/軽量の描画プリセットを用意できる設計にする。
- 影の描画距離・解像度・ライト数を制御する。
- Frustum Culling、LOD、InstancedMesh、共有Geometry/Materialを活用する。
- テクスチャサイズ・総メモリ量を管理し、必要に応じて圧縮形式を検討する。
- requestAnimationFrameのループは画面非表示時に停止し、画面離脱時にGeometry/Material/Texture/Rendererを適切にdisposeする。
- WebGL context lost/restoredを考慮する。
- iPhone Safari実機で移動、旋回、対象操作、マップ表示、戦闘遷移を確認する。

## 11. ミニマップ・全体マップ

既存Canvas 2D描画を維持し、3Dカメラの向きとプレイヤー位置を既存fieldStateから同期する。3D用に別の探索済み状態や別マップを作らない。ミニマップのタップ拡大、FOE表示、探索率表示を維持する。
