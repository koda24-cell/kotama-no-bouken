## 0. 今回のユーザー確認事項（最優先）

ユーザーがiPhone Safari上で確認した現行画面のスクリーンショットから、以下の問題が明確になった。

### 0-1. 迷宮画面の重大な問題

- 迷宮マップの描画領域が大きく、画面の大半を占めている。
- マップの表示範囲・縮尺・配置が画面サイズに対して適切でない。
- 地図の外周や未踏破領域が広く、実際に必要な通路情報が小さく見える。
- 地図パネル、背後の緑色領域、別パネルの境界が重なって見える。
- MAP情報パネルが地図の直下に大きく配置され、探索画面が縦に長い。
- 凡例・座標・FOE情報が独立した大きなパネルを占有している。
- 十字キーが画面下端に寄り、一部がブラウザ下部UIと近接・隠れそうになっている。
- 右下のアクションボタンが画面端に寄り、DEVボタンと干渉している。
- 地図と操作ボタンが離れ、視線移動が大きい。
- 現在地マーカーが大きく、マスや周囲の情報を覆っている。
- 迷宮画面が「地図を眺める画面」になっており、探索中に必要な情報が直感的に把握しにくい。

### 0-2. 他画面の問題

- 共通ヘッダーが大きく、各画面の表示面積を圧迫している。
- ショップの商品情報が縦長カード中心で、比較・選択がしにくい。
- 装備カテゴリの折り返し・間延びが発生する。
- スキルツリーが横にはみ出し、ノードや詳細カードが画面外に切れる。
- ホーム画面のパーティ情報が横一列に圧縮され、各キャラクターの情報が読み取りにくい。
- 各画面でパネル幅・余白・文字サイズ・操作領域の設計が統一されていない。

この仕様書は上記の実画面問題を解消することを必須とする。単なる色・枠線・フォントの変更では不十分。

## 1. 目的とデザイン方針

『世界樹の迷宮 HD REMASTER』をUI/UXの基準として、探索・戦闘・編成・装備・育成の画面構成と操作感を全面的に再設計する。

ただし、世界樹の画面を画像として模写するのではなく、以下の設計思想を『コタマのぼうけん』の既存機能に合わせて実装する。

1. ゲームの主役となる領域を最も大きく、明確に見せる。
2. 補助情報は必要な時に必要な場所へまとめる。
3. 画面内の情報に明確な優先順位を付ける。
4. 一覧・詳細・操作を整理し、情報を縦に積み重ねるだけのUIをやめる。
5. スマートフォンではタップしやすさと画面内完結を優先する。
6. PCでは横幅を活かした一覧・詳細の並列表示を行う。
7. ゲームロジックと表示ロジックを分離し、UI改修による既存機能の破壊を防ぐ。

## 2. 最重要ルール：既存ゲーム機能の保護

今回の作業はUI全面改修であり、ゲーム内容の再設計ではない。

ユーザーの追加承認なしに、以下を変更してはならない。

- キャラクター・職業・能力値
- スキルの効果、必要SP、習得条件、最大レベル
- 装備・アイテムの性能、価格、装備制限
- 敵の能力値、弱点、耐性、AI
- FOEの移動・追跡・戦闘仕様
- 迷宮のマップデータ、壁、扉、隠し通路、階段、イベント配置
- 移動1入力1マスの仕様
- 宝箱・採集・サブイベントの報酬
- エンカウント・ターン・戦闘行動優先度
- セーブデータの構造、saveVersion、既存セーブ互換性
- ストーリー、イベント、BGM/SEの再生条件

表示に必要なデータ加工は許可するが、保存値・戦闘計算・探索判定を変えないこと。
既存データの移行やセーブ形式変更が必要と判明した場合は、実装前に理由と影響を報告して承認を得ること。

## 3. 画面全体の共通設計

### 3-1. 共通ヘッダー

現行の大きなヘッダーを縮小する。

常時表示するもの：
- 現在の画面名、またはゲームロゴ（画面に応じて切替）
- 所持ゴールド
- メニューボタン／戻る操作

「ホーム・編成・ショップ・強化・設定」の大型ボタンをすべての画面に常時並べない。メニューを開いた時に一覧表示する。

### 3-2. 画面領域

各画面は原則として以下の階層に整理する。

- ヘッダー：画面名・共通情報
- メイン領域：その画面で最も重要な内容
- サブ領域：選択対象の詳細・補助情報
- 操作領域：決定・戻る・移動など

ただし、迷宮・戦闘は専用レイアウトとし、一般画面の共通テンプレートを無理に適用しない。

### 3-3. レスポンシブ基準

スマートフォンを第一級の対応対象とする。特にiPhone Safariで確認する。

必須：
- 横方向のページ全体スクロールを発生させない。
- 固定幅の子要素で親領域を押し広げない。
- 長い文字列・ボタン・カードが画面外へはみ出さない。
- safe-area-insetを考慮し、下部操作がSafariのバーやホームインジケータと干渉しない。
- 固定ボタンがコンテンツ・DEVボタン・他の操作と重ならない。
- タップ領域を十分に確保する。
- スクロールが必要な場合は、画面全体ではなく対象領域に限定する。
- PC向けの2カラムをスマートフォンにそのまま縮小しない。

目安として、スマートフォン幅ではメイン情報を縦方向に整理し、PCでは一覧と詳細を横並びにする。具体的なブレークポイントは既存CSSを調査して決定する。

## 4. 迷宮探索画面（最優先）

### 4-1. 基本方針

迷宮画面を今回の最優先改修対象とする。

現状の巨大なマップパネル＋巨大な凡例パネル＋下部十字キーという構成を廃止し、世界樹の迷宮を参考に「探索画面が主役、地図は連携する補助情報」という構成にする。

重要：現在のグリッド移動・マップデータ・FOE・仕掛け・採集・宝箱等のロジックは維持する。マップ表示の作り替えとゲームロジックの作り替えを混同しない。

### 4-2. 画面の情報優先度

優先順位：
1. 現在の探索状況／迷宮のメイン表示
2. プレイヤーの向き・現在位置
3. 直近の移動操作
4. FOEやイベントなど危険・重要情報
5. 地図
6. 座標・階層・凡例などの補助情報

地図だけが画面の主役にならないようにする。

### 4-3. 地図の表示

現行の周囲9×9マス表示および探索済みマップ情報を調査し、以下を満たす。

- 地図は画面内に収まるサイズで表示する。
- 現在地マーカーは1マスを覆わない大きさにする。
- マーカーはプレイヤーの向きを明確に示すが、隣接マスの視認を妨げない。
- 現在地を中心にする場合、周囲の通路・壁・イベントが読み取れる縮尺にする。
- 未踏破領域を過度に広く表示しない。
- マップパネルの外側に別のマップや背後パネルが見えてしまう重なりを解消する。
- マップの縦横比を維持する。
- 座標や凡例のためにマップ表示領域が不自然に押しつぶされないようにする。
- 表示範囲を切り替えられる場合も、現在の探索情報と整合すること。

凡例は常時大きな独立パネルにしない。小型の凡例、折りたたみ、または地図ヘルプ内にまとめる。凡例の意味自体は維持する。

### 4-4. 探索画面の主表示

現行のフィールド構造を調査し、世界樹らしい探索体験に合わせてメイン表示を設計する。

- 現行の俯瞰マップだけを巨大表示する方式を避ける。
- 一人称視点・前方の迷宮表現を導入する場合は、現在のマップデータから壁・通路・扉等を安全に描画できるか先に調査する。
- 一人称表示のために新しい迷宮データや移動ロジックを勝手に追加しない。
- 一人称表示が現行データ構造と両立しない場合は、現在の探索方式を維持したうえで、視覚的に探索画面と地図を整理する代替案を提示する。
- 見た目だけの疑似3Dで壁・扉・通路の位置関係を誤認させない。

### 4-5. 操作ボタン

- 十字キーは画面下部の安全領域内に収める。
- 上下左右のボタンを均等に配置する。
- 画面端・Safari UI・DEVボタンと重ならない。
- 移動1入力1マスを維持する。
- 長押し連続移動は追加しない。
- 決定・調査ボタンは十字キーから押し間違えにくい位置に置く。
- 画面幅が狭い場合はボタンサイズと配置を調整する。
- ボタンが画面外へ切れる場合はレイアウト側を修正し、ユーザーにスクロールを強要しない。

### 4-6. FOE・探索イベント

- FOEの巡回・追跡状態を地図上で区別する。
- 重要なFOE情報は小さなステータス表示で把握できるようにする。
- 宝箱・採集・階段・仕掛け・隠し通路のアイコンは既存の意味を維持する。
- 近くに操作対象がある場合は、対象名と実行可能な操作を明示する。
- FOE接近時の危険表示は、探索の邪魔にならず、かつ見落とさない表示にする。

## 5. 戦闘画面

Claudeが戦闘UIを含めて全面的に担当する。

- 敵の表示領域を明確に確保する。
- 味方のHP/SP/状態異常を一目で確認できるようにする。
- コマンド選択と対象選択を明確に分ける。
- コマンド一覧を縦に整理し、画面外へはみ出さない。
- 選択中の敵・味方・コマンドを明確に強調する。
- 戦闘メッセージは敵や味方の表示を隠しすぎない。
- PCでは広い表示領域を使い、スマートフォンでは敵・味方・コマンドの優先順位を保った縦レイアウトにする。
- 現在の戦闘ロジック、行動優先度、対象判定、ダメージ、状態異常、アニメーションの発生条件を変更しない。
- 演出を変更する場合も、演出完了タイミングと実際の処理タイミングを混同しない。

## 6. ホーム画面

- ヘッダーを縮小し、ホームのメインコンテンツを広く取る。
- パーティメンバーを見やすく表示する。
- 立ち絵・名前・職業・レベル・HP/SPを整理する。
- 4人を無理に小さく横一列に並べない。PCとスマートフォンで適切な配置にする。
- STARTボタンを主操作として明確にする。
- 冒険の記録は独立した導線を設ける。
- 現在のパーティ・装備・ステータスを勝手に変更しない。

## 7. 編成画面

- パーティ枠と控えメンバー一覧を区別する。
- 選択中キャラクターの詳細を表示する。
- 登録・解除・並べ替え操作を分かりやすくする。
- パーティ人数制限や主人公の控え条件など既存仕様を維持する。
- スマートフォンでは選択中キャラの詳細を下部または別パネルに表示する。

## 8. ショップ・装備画面

### 8-1. ショップ

一覧と詳細を分離する。
一覧に表示する情報：
- 商品名
- アイコン
- 価格
- 所持数／購入可能数

選択時の詳細：
- 説明
- 能力値
- 装備可能条件
- 購入・売却操作

### 8-2. カテゴリ

既存カテゴリ（武器・防具・盾・杖・ナックル・アクセサリ・その他）を維持する。

- スマートフォンでカテゴリボタンが不自然に折り返さない。
- タブ、横スクロール式タブ、またはセレクタを検討する。
- 選択中カテゴリが明確であること。

### 8-3. 装備比較

- 現在装備と候補装備を並べて比較できる。
- 能力値の増減を明確に表示する。
- 装備可能条件を示す。
- 装備・解除操作を誤操作しにくくする。
- 装備性能・計算式・装備制限は変更しない。

## 9. 強化・育成画面

### 9-1. スキルツリー

- 現在の前提・派生関係を維持する。
- スマートフォンでツリー全体が画面外に切れない。
- ツリー領域とスキル詳細領域を分離する。
- 選択中ノードの詳細は読みやすい位置に表示する。
- ノードを押しやすいサイズにする。
- 取得条件・現在レベル・必要ポイント・取得ボタンを整理する。
- 横方向スクロールを採用する場合、ページ全体ではなくツリー領域だけに限定する。
- スキル効果・必要SP・取得条件・最大レベルを変更しない。

### 9-2. キャラクター切替

キャラクター選択を分かりやすくし、誰のスキルを編集しているか常に確認できるようにする。

## 10. 設定・図鑑・冒険の記録

- 共通の文字サイズ・パネル・余白を統一する。
- 設定のBGM/SE操作を維持する。
- 図鑑・探索記録の既存情報を維持する。
- セーブ・ロードを維持する。
- 表示整理のためにデータ保存形式を変更しない。

## 11. 実装アーキテクチャ・コード品質

実装開始前に現行 `development` のファイル構成と担当別作業を確認する。

- 現行の分割モジュール構成を維持する。
- 巨大な `script.js` や旧monolithic `field.js` にUI実装を再集中させない。
- UI表示・イベント結線・ゲームロジックを可能な限り分離する。
- 既存の関数・DOM ID・CSSクラスを調査してから変更する。
- 不要な重複CSSや上書きCSSを増やさない。
- 固定値で画面幅を決め打ちしない。
- CSSのoverflow、position、z-index、safe-area、viewport単位を確認する。
- 画面切替時にイベントリスナーを重複登録しない。
- キャッシュバージョンを更新する。
- 変更ファイル・変更理由をPRに記載する。

## 12. 実装順序・段階レビュー

一度にすべての画面を変更して壊すことを避けるため、以下の段階に分ける。

### Phase 0：現状調査・画面設計
- developmentの最新コードを確認。
- 既存UIとCSS構造、DOM、JSイベントを調査。
- 画面ごとの現状・問題・変更対象ファイルを一覧化。
- 世界樹を参考にしたレイアウト案を作成。
- 既存ロジックに影響しない実装計画を提示。

### Phase 1：共通UI・レスポンシブ基盤
- ヘッダー・メニュー縮小
- 余白・パネル・文字・ボタンの共通ルール
- safe-area対応

### Phase 2：迷宮探索画面
- 最優先で改修
- メイン探索表示・地図・凡例・座標・操作領域を再配置
- スマートフォンでの視認性を改善
- FOE・イベント・マップ操作を維持

### Phase 3：戦闘画面
- Claudeが担当
- コマンド・敵・味方・メッセージを再配置
- 既存戦闘ロジックを維持

### Phase 4：ホーム・編成・ショップ・装備・育成
- 各画面を順次改修
- スキルツリーの見切れを解消
- 商品・装備の比較を改善

### Phase 5：全画面統一・回帰テスト
- 設定・図鑑・冒険記録を含む全画面確認
- PC/iPhone表示確認
- セーブ・ロード・探索・戦闘・育成の回帰確認

各Phaseの完了時に変更内容・スクリーンショット・テスト結果・未解決点を報告する。

## 15. Claudeへの作業指示

Claudeはこの仕様書と最新の `development` を基準に、UI全面改修の主担当として作業する。

まずPhase 0を実施し、現行コードと既存機能を調査する。調査を飛ばしてCSSを追加したり、DOMを全面置換したりしない。

その後、Phase 1から順に実装する。迷宮探索画面を最優先に、ユーザーのスクリーンショットで確認された見にくさ・重なり・画面外へのはみ出しを根本解決する。

戦闘画面も含め、全画面の統一を担当する。作業が大きい場合はPRを複数に分割し、各段階で動作確認できる状態を保つ。

実装上の判断が仕様と衝突する場合、ゲームロジックやセーブデータへ影響する場合、または一人称迷宮表示の実現に追加データが必要な場合は、独断で変更せず選択肢と影響を報告する。
